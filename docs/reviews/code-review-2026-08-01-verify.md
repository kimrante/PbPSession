# 검증 보고서 — v0.9.2/v0.9.3 수정 반영 확인 · 잔여 지시서 (2026-08-01)

렌더링·폴링 지시서(P0~S4)와 이미지 정리(L3)를 반영한 v0.9.2(`3d672c1`)·v0.9.3(`bdf3ee7`)에 대한 검증 결과 —
① 수정이 올바르게 반영됐는지, ② 크래시, ③ 통신 메시지 씹힘(유실), ④ 이미지 캡처 정상 동작.
**다른 세션에서 이 문서만 보고 잔여 수정을 진행할 수 있도록** 항목마다 위치·재현·수정 방향을 명시한다.
기준 커밋: `bdf3ee7`. 라인 번호는 이 커밋 기준.

## 총평

- **반영 검증: 대부분 정확.** M1(실제 경과 간격 기반 윈도 — 전환 구멍 완전 봉쇄), M2(Main 홉 + 자가 치유
  필터), P1·P2·P4, R1~R7(Android), S1~S4, ImageGc(메시지 `senderImagePath` 참조 보호 — 가장 위험한 함정을
  정확히 회피) 전부 올바르게 구현 확인. S3 파서 재작성은 별도 포팅 후 **20만 건 랜덤 퍼징**으로 행·문자
  소실·인덱스 오류 전무 확인.
- **크래시: 0건.**
- **잔여 핵심 2건**: V1 — 메시지 씹힘 경로 1건이 남아 있다(데스크톱 수신, createdAt 커서 vs 지연 커밋).
  V2 — 캡처 클리핑 수정(이분 재분할)이 **Android에만 이식**되어 데스크톱은 여전히 무통보 클리핑 가능.
- **캡처 신뢰도**: Android **높음**(측정이 최종 결정자, 이분 종료성 증명, 넘치면 시각적 에러, 프리로드
  실효, 공유 레이스 봉쇄). 데스크톱 **중간**(V2 해소 전까지).

권장 수정 순서: **V1 → V2 → V3~V7 → 기록 항목**.

## V1. [높음] 메시지 씹힘 잔여 경로 — 데스크톱 커서가 클라이언트 createdAt 기준이라 "지연 커밋" 메시지를 영구 누락

- **위치**: `desktop/src/main/kotlin/com/pbp/desktop/data/Firestore.kt:486-491`(커서·윈도가 `createdAt`
  기준 쿼리), `shared/.../SyncMapping` 계열 — `createdAt`은 **발신자가 작성한 시점의 클라이언트 시계**
  (Android `SyncMapping.kt:24`, 데스크톱 `RoomSync.kt:143`). 커밋 시각과 createdAt은 임의로 벌어질 수 있다.
- **재현 (구체 시나리오)**:
  1. Android가 오프라인 상태에서 10:00에 메시지 M 작성 — 로컬 삽입은 성공, Firestore 쓰기는 SDK 오프라인
     큐(또는 아웃박스)에 대기.
  2. 데스크톱이 10:01에 자기 메시지 D 전송(REST — 즉시 커밋) → 데스크톱 폴이 D를 수신, 커서가 10:01로 전진.
  3. Android가 10:02에 재접속 → M이 **createdAt=10:00으로 커밋**.
  4. 데스크톱 다음 폴은 `createdAt ≥ 10:01 − 윈도(활성 5초)`만 조회 → **M은 영구히 안 보이고, 그 구멍이
     `RoomCacheStore` 파일 캐시에 영속화**된다. (M1 수정은 "폴 공백"을 덮을 뿐 "커밋 지연"은 못 덮는다.)
  - Android↔Android는 리스너가 createdAt 무관하게 ADDED를 전달하므로 무영향. 데스크톱 수신 경로만 해당.
  - 보류했던 P3-2(서버 타임스탬프)의 실전 발현형이다.
- **수정 방향 (택1)**:
  1. **서버 타임스탬프 커서(권장)**: 모든 메시지 쓰기에 `syncAt: FieldValue.serverTimestamp()`(REST는
     `REQUEST_TIME` transform) 필드를 추가하고, **데스크톱 폴 커서·윈도를 syncAt 기준으로 전환**. 표시
     순서는 기존 createdAt 유지(스키마 전환 최소화 — 정렬·표시는 무변경). 구버전 문서(syncAt 없음)는 초기
     전체 로드에서만 만나므로 폴백은 createdAt. `Protocol`에 필드 추가 + 양 클라이언트 쓰기 경로 + 데스크톱
     쿼리 2곳.
  2. **저비용 대안(임시)**: 방 진입·포커스 복귀 시(그리고 유휴 N분마다 1회) `listMessages` 전체 대조를
     돌려 docId 기준 병합 — read 비용이 방 크기에 비례하므로 장기적으론 1안 권장.
- **테스트**: 시나리오 그대로 — Android 기내모드에서 작성 → 데스크톱에서 전송 → Android 복귀 → 데스크톱에
  M이 나타나는지. 수정 전엔 반드시 실패해야 정상.

## 기록 항목 (수정 불요 — 알려진 잔여로 인지만)

- **M2 잔여 창(이론적)**: 리셋 홉 착지 전에 폴 병합이 저장 스로틀을 통과한 경우, IO의 save와 delete가
  경합해 프로세스 SIGKILL과 겹치면 재시작 시 부활 가능 — 인메모리는 홉이 정리하고 다음 save가 덮어씀.
  `deletedDocIds` 영속화 또는 delete를 홉 안으로 옮기면 완전 봉쇄되나 우선순위 낮음.
- **ImageGc × 원격 아바타 다운로드 창**: 시작 직후 스윕과 다운로드가 겹치면 파일이 지워질 수 있으나
  경로가 결정적이라 다음 resolve가 재생성·자가 치유(기존 메시지도 함께 복구됨).
- **캡처 R2 상한의 성격**: 총 높이 32,000px 상한은 추정 기반 거부라 실측 초과분(~1.5×)의 일시적 오버슈트
  가능(~140MB) + 재렌더 중 구 페이지 병존으로 피크 ~2× — 강한 완화이지 절대 보장은 아님. 수용.
- **프리뷰 busy가 회전 시 리셋**: 홀더 스코프 재렌더와 겹치면 중복 재렌더 1회(recycle 폐지로 크래시
  불가) — 수용.
- **ImageGcTest가 판정 규칙만 검증**: 참조 집합 조립(가장 위험한 부분)은 미테스트 — sweep을 순수 함수로
  추출하면 커버 가능(선택).

  recycle 폐지(GC 위임). **R5**: 데스크톱 렌더러 예외 전파(안내만 V3). **R7** 4건 전부(단일 메시지 캡처·

### 메시지 씹힘 전수 조사 (V1 외 전부 안전)
